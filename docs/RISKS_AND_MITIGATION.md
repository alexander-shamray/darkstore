## Ключевые риски (Топ-5)

### 1. Сложности с интеграцией 1С (Самый критичный риск)
- **Почему опасен:** 1С — основа складского учёта. Без него проект не сможет работать.
- **Как снижать:**
  - Начать интеграцию в первый месяц.
  - Привлечь специалиста по 1С (аутсорс из Алматы/Астаны).
  - Использовать OData + готовые коннекторы.
  - Создать тестовую среду 1С заранее.

### 2. Низкий спрос в первые месяцы
- **Почему опасен:** Без заказов проект не окупится.
- **Как снижать:**
  - Запустить закрытое бета-тестирование через сеть АЗС.
  - Предложить первые 100 заказов с большой скидкой.
  - Активно продвигать через Telegram-каналы и Instagram города.

### 3. Выгорание соло-разработчика
- **Почему опасен:** Один человек несёт всю техническую нагрузку.
- **Как снижать:**
  - Жёсткое планирование и приоритизация задач.
  - Использовать готовые решения (MediatR, шаблоны).
  - Выделять 1 день в неделю на отдых.
  - Привлекать фрилансеров на отдельные задачи (Angular, интеграции).

### 4. Проблемы с доставкой и курьерами
- **Почему опасен:** Доставка — это лицо сервиса.
- **Как снижать:**
  - Нанять больше курьеров, чем нужно на старте.
  - Внедрить систему мотивации и штрафов.
  - Использовать данные Google Maps для оптимизации маршрутов.

### 5. Технический долг
- **Почему опасен:** Быстрый старт часто приводит к "костылям".
- **Как снижать:**
  - С самого начала использовать Clean Architecture.
  - Проводить рефакторинг раз в 2 месяца.
  - Писать тесты для критичных частей системы.

## Fault Tolerance Playbook по каждому риску

### Риск 1: Сложности с интеграцией 1С
**Технические меры устойчивости:**
- Circuit Breaker (50% fail rate → 1 мин break) через `Microsoft.Extensions.Http.Resilience`
- Hangfire retry: не более 5 попыток с exponential backoff на recurring job
- `IsStaleInventory` флаг: продажи продолжаются на кэшированных данных
- WireMock.Net mock-сервер для независимой разработки при недоступности тестовой 1С
- **Runbook:** При outage 1С > 2 часов — ручная корректировка топ-20 остатков через Admin Panel

### Риск 2: Задержки с интеграцией Kaspi Pay
**Технические меры устойчивости:**
- Kaspi Pay: HMAC-SHA256 webhook verification обязателен (защита от поддельных платежей)
- UNIQUE INDEX на `Payments.TransactionId` — идемпотентность webhook
- Outbox Pattern: webhook processing в Hangfire, ack Kaspi немедленно
- **Fallback:** Наличная оплата при доставке как альтернатива на случай технических работ Kaspi

### Риск 5: Выгорание соло-разработчика / Key Person Risk
**Технические меры устойчивости:**
- **Документирование всех паролей и ключей** в менеджере паролей (не только в голове разработчика)
- **IaC через Bicep** — инфраструктура воссоздаётся за < 30 мин без участия автора
- **Runbook** (этот документ + `OPERATIONS_MANUAL.md`) доступен команде, не только разработчику
- **Фиксированные версии всех зависимостей** — новый разработчик может собрать проект без изменений

### Риск 8: Проблемы с масштабированием (нагрузка)
**Технические меры устойчивости:**
- Azure App Service Auto-Scale rules (CPU > 70% → +1 instance)
- Rate Limiting на API endpoints: `AspNetCoreRateLimit` или встроенный `RateLimiter` (.NET 7+)
- Read replicas через Dapper на read-only connection string (второй эндпоинт Azure SQL)
- **Graceful degradation под нагрузкой:** Отключить AI-функционал → снизить нагрузку на DB через повышение TTL Redis кэша → включить queue для новых заказов

### Риск 10: Регуляторные риски (Закон РК №94-V)
**Технические меры устойчивости:**
- `PersonalDataDbContext` — физически изолированный DbContext
- Architecture Test (NetArchTest.Rules): автоматическая проверка, что ПДн не попадают в `AppDbContext`
- Audit Logging всех операций с ПДн в отдельный лог (не Azure, а KZ Local)
- **Runbook при утечке данных:** Немедленно уведомить регулятора (72 часа по GDPR/аналог РК), приостановить обработку ПДн, провести forensic analysis

### Риск 14: Доступность KZ Local DB — единственная точка отказа
**Технические меры устойчивости:**
- SQL Server Always On Availability Group или PostgreSQL Streaming Replication на второй KZ VPS
- Health Check с отдельным endpoint `/health/kz-db` — мониторинг каждые 30 сек
- Автоматический failover через DNS (Keepalived / Corosync) — переключение за < 60 сек
- JWT stateless auth: аутентифицированные сессии работают даже при KZ DB outage (токены проверяются локально)
- **RTO:** < 5 минут при наличии standby-реплики; < 60 минут при восстановлении из бэкапа

### Риск 15: Payment & Promo Fraud
**Технические меры устойчивости:**
- OTP rate limiting: `OtpRateLimiter` в Redis (3/час/телефон)
- `OtpCodes.Attempts` ≤ 5 с блокировкой после 5 неуспешных попыток
- UNIQUE INDEX `Payments.TransactionId` — Physical DB constraint, нельзя обойти
- `PromoCodes.PerUserLimit` — проверяется на уровне Application layer + DB constraint
- App Insights: автоматический алерт при > 10 failed OTP attempts за 5 мин с одного IP
