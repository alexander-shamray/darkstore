# Персональные данные и хостинг в Казахстане

**Проект:** Dark Store — быстрая доставка продуктов
**Локация:** Костанай, Казахстан
**Дата:** Октябрь 2026
**Цель:** Разобрать, где в текущем коде лежат персональные данные (ПДн), как
их стирать, и где можно размещать систему с учётом Закона РК №94-V.

> ⚠️ Это инженерный разбор, а не юридическое заключение. Всё, что касается
> толкования закона, — вопросы к юристу (см. §6 и
> [Правовые требования](LEGAL_REQUIREMENTS.md) §3.2).

## 1. Как сейчас устроено хранение

| Хранилище | Что там | Где физически |
|-----------|---------|---------------|
| `PersonalDataDbContext` (`KzLocalConnection`) | `Users` (ФИО, телефон, email, БИН), `Addresses`, `CourierProfiles` (ФИО, телефон, ИИН) | Казахстан |
| `AppDbContext` (`AzureConnection`) | `Orders`, `OrderItems`, `Couriers`, `Deliveries` | Azure, Sweden Central |

Базы связаны только общим GUID без внешнего ключа: `Order.UserId` → `User.Id`,
`Courier.Id` = `CourierProfile.Id`. Комментарий в `AppDbContext.cs` и
`CLAUDE.md` обещают: в Azure SQL нет ПДн.

## 2. Найденные проблемы

### 2.1 Адрес доставки лежит в Azure SQL — главное

`Order` хранит снимок адреса: `DeliveryStreet`, `DeliveryBuilding`,
`DeliveryApartment`, `DeliveryLatitude` / `DeliveryLongitude` и
`DeliveryDisplayLabel` вида «ул. Сатпаева, 7, кв. 12»
(`src/DarkStore.Domain/Orders/Order.cs`, `OrderConfiguration.cs`).

Снимок задуман сознательно: «FIX 1.2» убрал внешний ключ между базами. Но в
результате адрес и координаты квартиры клиента оказались в Швеции. Собственная
таблица запретов в [Логирование и аудит](LOGGING_AND_AUDIT_STRATEGY.md) §9
прямо относит «адрес доставки» к ПДн.

Вторая деталь: комментарий в `PlaceOrderCommand` говорит, что адрес
«snapshotted from KZ Local DB by the caller». На деле
`PlaceOrderCommandHandler` берёт улицу и координаты прямо из запроса, а из базы
KZ ничего не читает.

### 2.2 Стирания нет вообще

- `User.SoftDelete()` только ставит `IsDeleted = true`; ФИО, телефон и email
  остаются в таблице.
- Для курьеров (`CourierProfile`) нет даже soft delete.
- Каскад `Users → Addresses` сработает только при жёстком удалении, а его
  никто не вызывает.
- `Order.UserId` и снимок адреса в Azure никто не анонимизирует.

### 2.3 Запланированный аудит сохранит удалённые данные на 7 лет

В [Логирование и аудит](LOGGING_AND_AUDIT_STRATEGY.md) §10 описан
`AuditSaveChangesInterceptor`. При удалении он пишет `OldValues` — все колонки
удаляемой строки — в `AuditLogs`: неизменяемый журнал в Azure SQL со сроком
хранения 3 года, потом архив на 7 лет (§16).

Удаляем заказ — его адрес попадает в журнал, который по замыслу нельзя ни
изменить, ни удалить. Если повесить перехватчик на `PersonalDataDbContext`, в
Azure уедут и ФИО, и ИИН.

### 2.4 «UserId — не ПДн» — это предположение, а не факт

[Логирование и аудит](LOGGING_AND_AUDIT_STRATEGY.md) §9 разрешает писать
`UserId` в логи и Application Insights, потому что «не ПДн». Но id псевдонимен,
а не анонимен: он связан с `Users` в KZ. Для журнала на 7 лет разница
существенная. Решать юристу; в коде до его ответа лучше считать id ПДн.

Отдельно о курьерах: координаты курьера в реальном времени
(`Courier.CurrentLatitude`, `Delivery.CurrentLatitude`) лежат в Azure и через
общий GUID привязаны к ФИО и ИИН в KZ. Это ПДн работника.

### 2.5 Мелочь: часовой пояс

`BaseEntity` в комментариях говорит об UTC+6 для Казахстана. С 1 марта 2024
года Казахстан живёт в едином поясе UTC+5, `Asia/Almaty` — тоже UTC+5.
Комментарий устарел.

## 3. Что сделать в коде

1. **Карта данных.** Документ, где для каждой таблицы, лога и внешнего сервиса
   указано: что в нём о человеке, сколько хранится, как стирается (удаление,
   анонимизация или только срок хранения) и в какой стране лежит. Проблема 2.1
   обнаружилась бы при заполнении первой же строки.
2. **Адрес заказа: либо в KZ, либо анонимизировать.** Перенести снимок в KZ
   рядом с `Addresses` и ссылаться на него по id снимка — или оставить в Azure
   и затирать по сроку хранения после `Delivered`. Первый вариант честнее по
   отношению к закону №94-V.
3. **Одна команда `EraseUser`.** Две базы — это два SQL-сервера без общей
   транзакции, поэтому порядок важен:
   1. анонимизировать в Azure (`UserId` → пустой GUID, адрес очистить);
   2. затем жёстко удалить в KZ;
   3. команда идемпотентна по id запроса, её можно безопасно повторить.

   Обратный порядок хуже: при сбое после удаления в KZ в Azure останется адрес,
   который уже не к кому привязать.
4. **Стирание курьера.** Отдельный путь: данные работника хранятся по трудовым
   срокам, потом анонимизируются.
5. **Аудит хранит хэш, а не данные.** Перехватчик не пишет `OldValues` для
   сущностей с ПДн. Факт стирания записывается отдельной строкой с
   `SHA-256(RequestId ‖ UserId)` вместо самого id.
6. **Тест, который сканирует всё.** Стереть пользователя с доставленным
   заказом, затем пройти по всем колонкам обеих баз и не найти ни id, ни текста
   адреса.

## 4. Если переводить на архитектуру blueprint-backend

[blueprint-backend](https://github.com/alexander-shamray/blueprint-backend) —
платформа микросервисов на тех же технологиях (.NET, SQL Server, CQRS), где
эти вопросы уже решены правилами. Перевод darkstore на неё — сценарий
«адоптера» (ADR-062): платформа (building blocks, гейты, скаффолд) остаётся,
домен заменяется, а резидентность, согласия, налоги и фискализация (ОФД) —
то, что приносит сам проект.

### 4.1 Резидентность: разделение на две базы исчезает

Blueprint решает её по-другому (ADR-053, правило 3): **отдельный деплой на
каждую юрисдикцию** — свои базы, realm Keycloak, брокер и хранилище логов, и
всё это работает в стране. Поэтому `PersonalDataDbContext` и `AppDbContext`
пропадают, а проблемы 2.1 и 2.4 закрываются самой структурой.

### 4.2 Как сервисы darkstore ложатся на blueprint

| Darkstore | В blueprint | Что меняется |
|-----------|-------------|--------------|
| `Users` | **Keycloak** как владелец контакта (ADR-052) | Вход по телефону и OTP в realm; атрибуты `phone_number`, `locale` |
| `Addresses` | Сохранённый адрес (blueprint #473) | Пока его нет — адрес вводится при заказе |
| `Orders` + снимок адреса | **Ordering** | Адрес в `Orders`, при стирании анонимизация; правило «доставка бесплатна от 10 000 ₸» |
| Остатки | **Inventory** + `StoreId` | Несколько тёмных складов |
| Оплата | **Payments** + фискальный чек | ОФД — внешний обработчик данных, задаётся в конфигурации |
| `Delivery`, `Courier` | **Delivery** вместо **Shipping** | Свои курьеры вместо внешнего перевозчика; живая геопозиция курьера очищается после доставки |
| `CourierProfile` | **Couriers**, новый сервис | Новый субъект ПДн — работник |
| Уведомления | **Notifications** + SMS | В blueprint сейчас только email |
| Баллы, семейные группы | **Loyalty**, позже | — |
| — | **Privacy** | Хореография стирания по всем сервисам (blueprint #440) |

### 4.3 Чего blueprint пока не умеет (понадобятся ADR в нём самом)

- **Стирание работника.** Спек стирания в blueprint прямо исключает
  сотрудников; нужен вид субъекта (`Customer` / `Worker`) в запросе на
  стирание и свой набор участников для каждого вида.
- **SMS как канал** и телефон как контакт из Keycloak (сейчас только почта).
- **Аудит со старыми значениями** не переносится: в blueprint стирание
  фиксируется записью с хэшем, без самих данных.

### 4.4 Конфигурация юрисдикции KZ

Только значения, не код: языки `{kk, ru}`, пояс `Asia/Almaty`, валюта KZT,
сроки хранения (адреса, журнал уведомлений, трудовые) — цифры от юриста.

## 5. Хостинг

### 5.1 Что говорит закон

Статья 12 п. 2 Закона №94-V (в редакции с 2016 года) требует хранить ПДн «в
базе, находящейся на территории Республики Казахстан». Трансграничную передачу
регулирует отдельно статья 16 и разрешает её при условиях (страна-получатель
обеспечивает защиту либо есть согласие субъекта).

Распространённое толкование: **основная база обязана быть в KZ**, а копия или
обработка за рубежом — уже трансграничная передача со своими условиями.

> ⚠️ Текст статей не сверен с актуальной редакцией. В 2026 году закон менялся
> (закон №248-VIII — со 2 марта 2026; закон №311-VIII — с 1 января 2027;
> Цифровой кодекс). Затрагивают ли поправки статью 12 — проверить по
> adilet.zan.kz.

### 5.2 Azure

Региона Azure в Казахстане нет (на октябрь 2026 следов его появления не
найдено). «Выбрать регион Azure в KZ» не получится.

### 5.3 Три варианта размещения

| Вариант | Что где работает | Плюсы | Минусы |
|---------|------------------|-------|--------|
| **A. Весь деплой в KZ** | Все сервисы, базы, брокер, Keycloak и логи — у провайдера с ЦОДом в KZ | Вопросы о трансграничной передаче почти снимаются | Managed-сервисов меньше, чем в Azure; надёжность и цены проверять |
| **B. Гибрид** (текущая модель) | Сервисы с ПДн и их базы в KZ, остальное в Azure | Azure используется там, где можно | Брокер и логи общие, в них id клиентов; трансграничная передача всё равно есть |
| **C. Azure Local / Arc или AWS Outposts в KZ-ЦОДе** | Всё физически в KZ, управление из облака | Инструменты Azure / AWS сохраняются | Дорого; метаданные управления уходят за рубеж — вопрос к юристу |

**Инженерный аргумент против B:** сервис и его база должны стоять рядом. API в
Швеции и SQL в KZ — десятки миллисекунд на каждый запрос, и EF превращает один
HTTP-вызов в секунды. Именно так устроено сейчас: API в Sweden Central ходит в
KZ DB при авторизации. Значит, в KZ уезжает не таблица `Users`, а целиком
каждый модуль, который работает с ПДн, — то есть почти всё.

Azure можно оставить там, где нет ПДн: CI/CD, реестр образов (если в образах
нет данных), сайт документации на Static Web Apps.

### 5.4 AWS

- **Региона AWS в KZ нет**, объявленного тоже.
- **AWS Outposts** — стойки AWS, которые Amazon ставит и обслуживает в вашем
  ЦОДе или у колокейшн-партнёра. С января 2026 года Outposts второго поколения
  можно поставлять в Казахстан; в 2023 году Минцифры подписало с AWS соглашение
  о пилоте. На стойке работают EKS, RDS (в т. ч. SQL Server), EBS, S3 on
  Outposts; данные лежат в KZ, управление идёт из родительского региона AWS за
  рубежом. Это стойка с многолетним контрактом — для стартапа, скорее всего,
  избыточно.
- **Freedom Cloud × AWS** (апрель 2025) — по найденным источникам это доступ к
  программам и Marketplace, а не регион AWS.

### 5.5 Облака с ЦОДами в Казахстане

| Провайдер | Кто это | Managed Kubernetes | Комментарий |
|-----------|---------|--------------------|-------------|
| **Yandex Cloud** (регион KZ) | ТОО «Облачные Сервисы Казахстан», ЦОД в KZ с 2024 года | Да | Самый широкий набор managed-сервисов; managed SQL Server в KZ-регионе — проверить |
| **VK Cloud** (с QazCloud) | Локализованная платформа с 2023 года; QazCloud — группа «Самрук-Қазына» | Да | Реестр образов, мониторинг, Ingress |
| **PS Cloud** (PS.kz) | Местный провайдер | Да, заявлен | Один из старейших в KZ |
| **Freedom Cloud** | Freedom Holding | Kubernetes, S3, GPU | Новый ЦОД в Алматы строится, срок — 2027 |
| **Hyper Cloud** (Beeline KZ) | Оператор связи | Да | — |
| **Servercore, Serverspace, Kazteleport** | Ниша IaaS / VDS | Заявлен | Скорее виртуальные машины, чем managed-платформа |

Данные о Kubernetes взяты в основном из обзоров и маркетинговых страниц;
зрелость и SLA проверять у самих провайдеров.

**SQL Server — главный фильтр.** У местных облаков managed-версии чаще всего
нет (лицензии Microsoft). Варианты: держать SQL Server самим (в Kubernetes или
на ВМ) с покупкой лицензии — или перейти на PostgreSQL. RabbitMQ, Redis и
Keycloak от провайдера не зависят. Логи и трейсы — свой стек на
OpenTelemetry в KZ вместо Application Insights.

**Нетехнический фактор:** Yandex Cloud и VK Cloud — компании российского
происхождения, хотя работают через казахстанские юрлица. Допустимость с учётом
санкций, инвесторов и партнёров — решение бизнеса.

### 5.6 Рекомендация

1. **Yandex Cloud KZ или VK Cloud** как основа с managed Kubernetes; если
   решающими окажутся политические соображения — **PS Cloud или Freedom
   Cloud**.
2. Рядом — SQL Server самостоятельно, либо отдельное решение о переходе на
   PostgreSQL.
3. AWS Outposts — только при жёстком требовании «обязательно AWS» и бюджете
   уровня enterprise.

Это согласуется с выводами [Azure Lock-In Analysis](AZURE_LOCK_IN_ANALYSIS.md):
домен и Application не зависят от Azure, привязка сосредоточена в
инфраструктуре.

## 6. Вопросы юристу

- [ ] Можно ли держать основную базу ПДн в KZ и при этом обрабатывать данные
