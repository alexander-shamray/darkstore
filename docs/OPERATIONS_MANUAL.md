# Операционная инструкция (Operations Manual)

**Проект:** Dark Store — быстрая доставка продуктов  
**Локация:** Костанай, Казахстан  
**Версия:** 1.0  
**Дата:** Май 2026

---

## 1. Введение

Данный документ описывает основные операционные процессы проекта Dark Store. Цель — обеспечить стабильную и качественную работу сервиса даже при росте количества заказов.

**Основные принципы:**
- Скорость и точность сборки заказов
- Высокий уровень сервиса для клиента
- Прозрачность и контроль всех процессов
- Постоянное улучшение на основе обратной связи

---

## 2. Структура команды (на старте)

| Роль                    | Количество | Основные обязанности                              |
|-------------------------|------------|---------------------------------------------------|
| **Операционный менеджер** | 1          | Общее управление, контроль качества, работа с 1С |
| **Сборщики заказов**     | 2–4        | Сборка заказов на складе                          |
| **Курьеры**              | 4–8        | Доставка заказов клиентам                         |

## 3. Основные операционные процессы

### 3.1. Приёмка товаров на склад

**Процесс:**
1. Товары приезжают от поставщиков (по графику).
2. Складской работник проверяет количество и качество.
3. Данные вносятся в 1С.
4. Товары размещаются по зонам хранения (A, B, C — по частоте спроса).
5. Система автоматически обновляет остатки.

**Важно:**
- Проверять срок годности при приёмке.
- Фиксировать брак и возвращать поставщику.
- Проводить инвентаризацию раз в неделю.

> 🛡️ **Fault Tolerance — Приёмка товаров:**
> - **1С недоступна при приёмке:** Заполни **бумажный лист приёмки** (шаблон хранится на складе). После восстановления 1С внеси данные вручную. Лист хранить 30 дней.
> - **Расхождение фактического и документального кол-ва:** Составь акт расхождения, подпиши с водителем поставщика, отфотографируй, отправь менеджеру. Не принимай товар на баланс до подтверждения.
> - **Сбой сканера штрих-кодов:** Вводи SKU вручную через планшет. Если планшет тоже недоступен — заполни бумажный приходной ордер, передай менеджеру немедленно.
> - **Поставщик привёз товар вне графика:** Принимай только при наличии места и свободного складского работника. Если мощностей нет — попроси поставщика вернуться через 2 часа, зафиксируй в журнале.
> - **Истёкший товар в партии:** Отделяй весь лот в карантинную зону, не смешивай с годным. Не принимай на продажу до выяснения. Уведоми поставщика письменно (WhatsApp достаточно с фото).
> - **Критический уровень запасов (< MinimumStock):** Система автоматически отправляет алерт в Telegram-канал "Склад". Дежурный менеджер обязан инициировать экстренный заказ у поставщика в течение 30 минут.

### 3.2. Сборка заказа (Pick & Pack)

**Процесс:**
1. Заказ поступает в систему.
2. Сборщик получает задание через приложение/планшет.
3. Собирает товары по списку (соблюдая последовательность зон).
4. Проверяет качество и свежесть продуктов.
5. Упаковывает заказ (использует фирменные пакеты).
6. Приклеивает стикер с номером заказа и QR-кодом.
7. Передаёт заказ в зону выдачи курьерам.

**Стандарты времени сборки:**
- Маленький заказ (до 10 позиций) — до 8 минут
- Средний заказ — до 12 минут
- Большой заказ — до 18 минут

> 🛡️ **Fault Tolerance — Сборка заказа:**
> - **Приложение/планшет недоступны:** Распечатай задание через кнопку «Печать» в веб-версии на резервном устройстве (ноутбук менеджера). Если интернет полностью недоступен — работай по последнему распечатанному плановому заданию и фиксируй сборки на бумаге.
> - **Товар не найден на указанном месте:** Проверь соседние ячейки (±2 ячейки). Если всё равно нет — сообщи менеджеру через рацию/мессенджер. Менеджер либо находит товар, либо исключает позицию из заказа и уведомляет клиента (частичная сборка со скидкой).
> - **Товар испорчен / истёк срок годности:** Не добавляй в заказ. Отметь в системе "Списание по качеству". Передай на карантин. Если нет замены — частичная сборка с уведомлением клиента.
> - **Перепутаны позиции в заказе:** При обнаружении на этапе QR-проверки — переберать заново. При обнаружении у клиента — курьер забирает неправильный товар, магазин компенсирует +500 бонусных тг.
> - **Принтер стикеров не работает:** Пишите номер заказа маркером на пакете. Критично: без номера курьер не возьмёт заказ — используй резервный ролл ручных наклеек (хранится в ящике у менеджера).
> - **Массовый наплыв заказов (пиковые часы):** При очереди > 5 заказов — менеджер подключает дополнительных сборщиков (по плану пиковых часов) и временно скрывает некоторые категории для новых заказов.

### 3.3. Процесс доставки

**Процесс:**
1. Курьер получает заказ в приложении.
2. Забирает заказ со склада.
3. Едет к клиенту (использует навигатор).
4. Связывается с клиентом при подъезде.
5. Передаёт заказ и получает подтверждение.
6. Отмечает заказ как выполненный в приложении.

**Важные правила:**
- Курьер должен быть в фирменной одежде.
- Запрещено открывать пакет с заказом.
- При проблеме (клиент не отвечает) — звонить в поддержку.
- Максимальное время доставки — 30 минут с момента сборки.

> 🛡️ **Fault Tolerance — Процесс доставки:**
> - **Приложение курьера недоступно:** Курьер звонит диспетчеру поддержки (+7 XXX XXX XX XX), получает адрес голосом. По завершении — диспетчер вводит статус вручную.
> - **Навигатор не работает / нет интернета:** Каждый курьер обязан знать 5 ключевых районов доставки по памяти. На телефоне должна быть офлайн-карту Костаная (Maps.me или 2GIS). Если потерялся — звонит диспетчеру.
> - **Клиент не открывает дверь / не отвечает:** Звонить 2 раза с интервалом 3 минуты. Написать в WhatsApp. Если нет ответа 10 минут — звонить в поддержку. Поддержка инициирует перезвон. Если нет ответа ещё 10 минут — заказ возвращается на склад, клиент получает SMS с инструкцией.
> - **Авария / поломка транспорта:** Курьер немедленно звонит менеджеру. Менеджер назначает ближайшего свободного курьера. Клиент получает SMS с обновлённым временем доставки. Если задержка > 15 мин — клиент получает промокод -10%.
> - **Опасная ситуация (плохая погода, ДТП поблизости):** Курьер имеет право отказаться от доставки, позвонив менеджеру. Клиент уведомляется. Заказ переносится или отменяется с полным возвратом.
> - **Заказ повреждён при транспортировке:** Не передавать клиенту. Фотографировать ущерб. Возвращать на склад. Поддержка связывается с клиентом и предлагает повторную сборку или возврат денег.
> - **Несколько заказов одновременно (комбо-доставка):** Максимум 2 заказа на одного курьера одновременно. При > 2 — диспетчер назначает второго курьера. Нельзя брать третий заказ — деградация времени доставки критична для репутации.

### 3.4. Работа с возвратами и жалобами

**Типы возвратов:**
- **Полный возврат** — клиент отказался от всего заказа
- **Частичный возврат** — отдельные позиции
- **Жалоба на качество** — испорченный товар

**Процесс:**
1. Клиент обращается в поддержку.
2. Поддержка фиксирует обращение.
3. При необходимости — курьер забирает товар обратно.
4. Деньги возвращаются на карту / баланс лояльности.
5. Инцидент анализируется и фиксируется.

**Срок реакции на жалобу:** не более 30 минут.

> 🛡️ **Fault Tolerance — Возвраты и жалобы:**
> - **Платёжная система недоступна для возврата (Kaspi Pay downtime):** Зафиксируй возврат внутри системы статусом "Refund Pending". Повторно обработай через Hangfire retention job при восстановлении. Клиента уведоми: "Возврат будет зачислен в течение 24 часов".
> - **Клиент требует возврат > 48 часов после заказа:** Проверь статус по системе. Если заказ доставлен и подтверждён — запрос вне политики. Эскалируй на менеджера, не отказывай самостоятельно. Менеджер принимает решение.
> - **Массовые жалобы на один и тот же товар (партия):** Немедленно скрыть товар в каталоге (`IsActive = false` через admin panel). Уведомить склад об изоляции остатков. Проверить поставку. Это занимает максимум 10 минут — промедление = ещё больше жалоб.
> - **Система недоступна при жалобе:** Поддержка записывает данные в Google Sheets (резервная форма): номер заказа, телефон, проблема, решение. После восстановления — вносит в систему.
> - **Возврат наличными (если применяется):** Не более 2000 тг курьер может вернуть из кассы. Всё выше — через официальный возврат на карту или бонусы. Кассу курьера пополняет менеджер ежедневно в начале смены.
> - **Двойной возврат (мошенничество):** Система проверяет UNIQUE constraint на `Payments.TransactionId`. При попытке двойного возврата — система блокирует, поддержка получает уведомление, запрос передаётся менеджеру.

### 3.5. Работа с 1С

**Ежедневные задачи:**
- Синхронизация остатков (каждые 15 минут)
- Создание приходных накладных
- Формирование отчётов по продажам
- Корректировка остатков при возвратах

**Ответственный:** Операционный менеджер

> 🛡️ **Fault Tolerance — Работа с 1С:**
> - **1С недоступна (синхронизация не прошла):**
>   - Система автоматически активирует флаг `Inventory.IsStaleInventory = true` (видим только в Admin Panel).
>   - Circuit breaker открывается после 3 последовательных сбоев; повторные попытки — каждые 5 минут с exponential backoff.
>   - Продажи продолжаются по последним известным остаткам — допускается временное "избыточное" списание.
>   - При восстановлении 1С — немедленный полный sync (`RecurringJob.TriggerJob("1c-sync")`), а не ожидание следующего cron.
>   - Telegram-алерт отправляется менеджеру при первом сбое и при восстановлении.
> - **Рассинхронизация данных (остатки в 1С ≠ Dark Store):**
>   - Еженедельно (понедельник 09:00) запускать ручную сверку остатков через отчёт в Admin Panel.
>   - При расхождении > 5% — немедленная ручная корректировка.
> - **1С требует обновления / техработы:**
>   - Администратор 1С обязан предупреждать за 2 часа в Telegram-канал "Тех. команда".
>   - В период работ Active circuit breaker — продажи работают на кэшированных данных.
>   - После обновления — принудительный full sync.
> - **Долговременный сбой 1С (более 4 часов):**
>   - Провести ручную инвентаризацию критичных товаров (топ-20 по продажам).
>   - Ввести данные вручную через admin panel.
>   - Руководство принимает решение о режиме ограниченной работы.

## 6. Частые проблемы и решения

| Проблема                        | Возможная причина               | Решение                              |
|--------------------------------|----------------------------------|--------------------------------------|
| Товар закончился               | Ошибка в остатках 1С            | Срочно обновить остатки              |
| Курьер опаздывает              | Пробки / неправильный маршрут   | Использовать альтернативный маршрут  |
| Клиент не отвечает             | Телефон выключен                | Позвонить 2 раза, затем отменить     |
| Жалоба на качество товара      | Испорченный продукт             | Заменить + компенсация 500–1000 тг   |
| Ошибка в сборе заказа          | Невнимательность сборщика       | Дополнительное обучение + штраф      |

> 🛡️ **Расширенные fault tolerance сценарии:**
>
> | Проблема | Немедленное действие | Предотвращение |
> |---------|---------------------|---------------|
> | **API полностью недоступен** | Перейти на резервный режим: принимать заказы по телефону (+7 XXX), передавать вручную сборщику | Мониторинг `/health` каждые 1 мин, алерт за 2 мин простоя |
> | **KZ Local DB недоступна** | Временно заблокировать регистрацию и вход. Существующие токены работают (JWT stateless). Уведомить в Telegram | Standby-реплика (см. `RISKS_AND_MITIGATION.md` риск №14) |
> | **Azure SQL недоступна** | Приостановить приём заказов, выдать 503 с `Retry-After: 300`. Обработка уже принятых — через Outbox при восстановлении | Включить `geo-redundant backup`, настроить failover group |
> | **Redis недоступен** | Система работает напрямую через БД (деградация производительности, не падение). Fallback на `IDistributedMemoryCache` в Dev | Redis Standard C1 имеет SLA 99.9%; для prod избегать Basic C0 |
> | **Kaspi Pay API недоступен** | Принимать только наличные / показывать пользователю "Касса временно недоступна, выберите другой способ" | Circuit breaker; webhook идемпотентность через UNIQUE TransactionId |
> | **SMS провайдер недоступен** | Переключиться на резервного провайдера (ISmsService — заменяемый интерфейс). Если оба недоступны — включить email OTP как крайний fallback | Два провайдера (SMSC + KazInfoTech) в конфигурации |
> | **Интернет в офисе/складе отключился** | Работа по офлайн-листам (распечатанные задания). Курьеры используют мобильный интернет | Мобильный роутер как резервное подключение |
> | **Самовольная смена пользователем адреса во время доставки** | Курьер звонит поддержке; не меняет маршрут самостоятельно | В приложении заблокировать смену адреса после статуса "Курьер едет" |

## 7. Эскалация проблем

| Уровень | Кто решает                  | Время реакции |
|---------|-----------------------------|---------------|
| 1       | Специалист поддержки        | 15 минут      |
| 2       | Операционный менеджер       | 30 минут      |
| 3       | Руководитель проекта        | 1 час         |

**Контакты для эскалации:**
- Операционный менеджер: +7 XXX XXX XX XX
- Руководитель проекта: +7 XXX XXX XX XX

> 🛡️ **Fault Tolerance — Эскалация:**
> - **Если ответственное лицо недоступно:** Эскалируй на следующий уровень немедленно — не жди истечения времени реакции. Каждый уровень должен иметь резервного человека.
> - **Матрица инцидентов по критичности:**
>
>   | Тип инцидента | Время реакции | Кто уведомляется сразу |
>   |--------------|---------------|----------------------|
>   | API полностью недоступен | 5 минут | Все уровни + клиенты |
>   | Платежи не проходят | 10 минут | Уровень 2 + финансы |
>   | Утечка персональных данных | 15 минут | Уровень 3 + юрист (Закон РК) |
>   | Задержки доставки > 45 мин | 15 минут | Уровень 2 |
>   | Массовые жалобы (> 3 за 30 мин) | 20 минут | Уровень 2 |
>
> - **Postmortem (разборка инцидента):** Обязателен для каждого инцидента уровня 2+. Шаблон: Что случилось → Почему → Что сделали для устранения → Что сделаем чтобы не повторилось. Документируется в Notion в течение 24 часов.
> - **War Room (режим кризиса):** При инциденте уровня 3 — открыть голосовой чат в Telegram и не закрывать его до устранения инцидента.

## 8. Документация и отчётность

**Ежедневные отчёты:**
- Количество собранных заказов
- Среднее время сборки
- Количество возвратов и жалоб
- Загруженность курьеров

**Еженедельные отчёты:**
- Общий оборот
- Средний чек
- Уровень удовлетворённости клиентов (NPS)
- Проблемные зоны

> 🛡️ **Fault Tolerance — Отчётность:**
> - **Система недоступна в конце дня:** Менеджер вносит данные в резервную Google Sheets таблицу (ссылка хранится в закреплённом сообщении Telegram-канала). Синхронизирует с системой после восстановления.
> - **Отчёт не сходится с 1С:** Фиксируй расхождение и время обнаружения. Не исправляй задним числом без согласования финансиста. Расхождения > 5% требуют немедленного аудита.
> - **Резервная копия отчётов:** Все ежедневные отчёты автоматически экспортируются в PDF и сохраняются в Azure Blob Storage. Храниться 1 год.

## 9. Обучение персонала

Все новые сотрудники проходят:
1. Обучение работе с приложением (2 дня)
2. Стажировку на складе (3 дня)
3. Стажировку с курьером (2 дня)
| 4 | Тестирование знаний

> 🛡️ **Fault Tolerance — Обучение:**
> - **Обязательный раздел "Действия при сбоях"** включён в программу обучения с первого дня. Каждый сотрудник должен знать: как работать без приложения, куда звонить при каждом типе сбоя, как заполнять бумажные формы.
> - **Обновление инструкций:** При каждом крупном изменении системы — повторный инструктаж всего персонала (максимум 30-минутное собрание). Нельзя предполагать, что сотрудники самостоятельно читают обновлённую документацию.
> - **Контакты экстренной связи** — ламинированная карточка выдаётся каждому сотруднику при приёме на работу и после каждого обновления контактов.

## 10. Резервное копирование и восстановление данных (Disaster Recovery)

> ⚠️ **Данные — критический актив проекта.** Потеря базы заказов, остатков или клиентов недопустима. Этот раздел обязателен к исполнению с первого дня работы.

---

### 10.1. Целевые показатели восстановления

| Показатель | Значение | Описание |
|-----------|---------|---------|
| **RPO** (Recovery Point Objective) | **≤ 1 час** | Максимально допустимая потеря данных |
| **RTO** (Recovery Time Objective) | **≤ 1 час** | Максимальное время восстановления системы |
| **Цель доступности** | **99.5%** | ~3.6 часа простоя в месяц допустимо |

---

### 10.2. Azure SQL Database — стратегия бэкапа

Azure SQL автоматически создаёт резервные копии. Никакой дополнительной настройки для базового бэкапа не требуется.

#### Автоматические бэкапы (включены по умолчанию)

| Тип бэкапа | Частота | Хранение (Basic/S0) | Хранение (Standard S1+) |
|-----------|---------|---------------------|------------------------|
| **Full backup** | Раз в неделю | 7 дней | До 35 дней |
| **Differential** | Каждые 12 часов | 7 дней | До 35 дней |
| **Transaction log** | Каждые 5–10 минут | 7 дней | До 35 дней |

> 📌 **Настроить в Azure Portal:**  
> SQL Database → Backups → Retention policies → установить `Long-term retention: 35 days`

#### Long-Term Retention (LTR) — долгосрочные бэкапы

Настроить через Azure Portal или Azure CLI:

```bash
# Настройка LTR через Azure CLI
az sql db ltr-policy set \
  --resource-group darkstore-rg \
  --server darkstore-sql \
  --database DarkStoreDb \
  --weekly-retention P12W \
  --monthly-retention P12M \
  --yearly-retention P1Y \
  --week-of-year 1
```

| Тип | Период хранения | Назначение |
|-----|----------------|-----------|
| Weekly backup | **12 недель** | Защита от ошибок данных, обнаруженных спустя недели |
| Monthly backup | **12 месяцев** | Восстановление на конец месяца (финансовая отчётность) |
| Yearly backup | **1 год** | Архив и требования аудита |

### 10.4. Процедура восстановления (Point-in-Time Restore)

**Сценарий:** Случайное удаление данных, некорректная миграция, ошибка в коде.

**Шаг 1 — Определить момент восстановления**
```
Вопрос: "До какого момента данные были корректными?"
Пример: "Вчера в 14:30 всё было нормально, ошибка произошла в 15:00"
```

**Шаг 2 — Восстановление через Azure Portal**
1. Azure Portal → SQL Databases → `DarkStoreDb`
2. Нажать **Restore**
3. Выбрать **Point in time** → указать дату и время
4. Указать имя новой БД: `DarkStoreDb-restored-YYYYMMDD`
5. Нажать **Review + Create**

**Шаг 3 — Проверка восстановленной БД**
```sql
-- Проверить количество заказов
SELECT COUNT(*), MAX(CreatedAt) FROM Orders;

-- Проверить последние транзакции
SELECT TOP 20 * FROM Orders ORDER BY CreatedAt DESC;

-- Убедиться в целостности данных
SELECT COUNT(*) FROM OrderItems oi
LEFT JOIN Orders o ON oi.OrderId = o.Id
WHERE o.Id IS NULL; -- Должно быть 0
```

**Шаг 4 — Переключение приложения**
```bash
# Вариант А: Переименовать БД (если нужна полная замена)
# Azure Portal → SQL Server → Rename database

# Вариант Б: Обновить connection string в App Service
az webapp config appsettings set \
  --resource-group darkstore-rg \
  --name darkstore-api \
  --settings "ConnectionStrings__DefaultConnection=<new-connection-string>"

# Перезапустить приложение
az webapp restart --resource-group darkstore-rg --name darkstore-api
az webapp restart --resource-group darkstore-rg --name darkstore-api-staging
```

**Шаг 5 — Уведомить команду**
- Сообщить в рабочий Telegram-чат о факте восстановления
- Зафиксировать: причину инцидента, время простоя, объём потерянных данных
- Внести в журнал инцидентов

> ⏱️ **Ожидаемое время восстановления:** 20–40 минут (создание новой БД из бэкапа) + 10–20 минут (проверка и переключение) = **< 1 часа (RTO)**

### 10.6. Гибридная архитектура — локальный SQL Server (если применимо)

> Актуально при соблюдении Закона РК о персональных данных — если решено хранить данные локально.

**Настройка автоматических бэкапов через SQL Server Agent:**

```sql
-- Создать задание SQL Agent для ежедневного бэкапа
EXEC msdb.dbo.sp_add_job @job_name = N'DarkStore_Daily_Backup';

EXEC msdb.dbo.sp_add_jobstep
    @job_name = N'DarkStore_Daily_Backup',
    @step_name = N'Backup Database',
    @command = N'
        BACKUP DATABASE DarkStoreDb
        TO DISK = N''\\backup-server\darkstore\DarkStoreDb_'' +
            CONVERT(VARCHAR, GETDATE(), 112) + ''.bak''
        WITH COMPRESSION, CHECKSUM, STATS = 10;
    ';

-- Расписание: ежедневно в 02:00
EXEC msdb.dbo.sp_add_schedule
    @schedule_name = N'DailyAt2AM',
    @freq_type = 4,
    @freq_interval = 1,
    @active_start_time = 20000;
```

**Хранение локальных бэкапов:**
- Папка бэкапов: `\\backup-server\darkstore\`
- Хранить: последние **30 дней** (1 бэкап в день)
- Дополнительно: копировать в Azure Blob Storage раз в неделю как внеплощадочная копия

```bash
# Синхронизация бэкапов в Azure Blob (через AzCopy)
azcopy copy '\\backup-server\darkstore\*' \
  'https://darkstorestorage.blob.core.windows.net/db-backups/' \
  --recursive --overwrite=false
```
